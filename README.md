# 关灯科技实战任务 · 告警误报根因分析与处置优化

## 一、我的判断（看到了什么、根问题是什么）

### 看到了什么

数据 `alarm_records.csv` 共 1068 条告警记录，其中 1026 条已闭环核验（`is_valid` 非空），**112 条被确认为误报（误报率 10.9%）**，另有 42 条未完成闭环。

核心发现——**「心跳滞后时长」是误报最关键的驱动因素**。我把「监测探针触发告警的时刻（`trigger_time`）」减去「心跳最后同步时刻（`heartbeat_synced_at`）」，得到「心跳滞后时长（heartbeat_lag_sec）」，按滞后时长分桶看误报率，呈现强单调上升：

| 心跳滞后时长 | 样本数 | 误报率 |
|---|---|---|
| 0–60 秒 | 111 | **1.8%** |
| 1–5 分钟 | 217 | **3.2%** |
| 5–10 分钟 | 259 | **3.5%** |
| 10–20 分钟 | 196 | **9.7%** |
| 20–30 分钟 | 47 | **29.8%** |
| 30–40 分钟 | 55 | **32.7%** |
| 40–50 分钟 | 58 | **37.9%** |
| 50 分钟以上 | 83 | **25.3%** |

滞后 ≤ 10 分钟的告警误报率只有约 3%，而滞后 > 20 分钟后误报率飙升至 30% 以上。

同时，用决策树（`sklearn.DecisionTreeClassifier`，max_depth=3，5 折交叉验证）做特征重要性排序，结果一致：

| 特征 | 重要性 |
|---|---|
| heartbeat_lag_sec（心跳滞后） | **0.626** |
| 华东节点（monitor_node） | 0.194 |
| heartbeat_ttl_sec（心跳剩余秒数） | 0.179 |
| concurrent_qps（并发量） | 0.000 |

### 根问题

**大量误报的本质是「滞后心跳」**：当服务实例的心跳长时间没有同步（`heartbeat_synced_at` 距今很久），监测探针在心跳已过期/滞后时仍触发告警，把「心跳没按时上报」误判成「服务故障」。这类告警一旦派单，值班工程师排查后才发现是监控链路自身的问题（心跳采集延迟、网络抖动等），并非真实故障，于是沦为无效排查。

- `concurrent_qps` 与误报几乎无关（误报样本 52.9 vs 真实样本 51.6，无显著差异），说明**误报与真实业务负载无关**，进一步佐证根因在「心跳同步链路」而非「服务压力」。

## 二、我做了什么

我交付了一个**可解释、可落地、可复现**的「滞后心跳预标记」规则，而非黑盒模型——运维场景下，值班工程师需要知道「为什么这条告警被标记」，才能信任并配合。

**规则**：当 `trigger_time - heartbeat_synced_at > 900 秒（15 分钟）` 时，将告警预标记为「疑似滞后心跳导致的误报」，建议优先核实心跳链路而非直接介入业务排查。

选择 900 秒的原因：它是「净节省时间最大化」的拐点（见下）。规则仅依赖两个时间字段，无需任何模型、可直接写进现有告警派单逻辑。

配套交付（本仓库）：
- `analyze3.py`：完整的成本-收益测算与阈值扫描，可直接复现结论。
- `explore.py` / `analyze.py` / `analyze2.py`：数据探索与中间分析过程。
- `model.py`：决策树特征重要性验证（佐证 lag 是主导特征）。

## 三、怎么证明有用（数字全部由发放数据算出，可复现）

口径（题目给定）：**每次误报排查损失 75 分钟；每提前标记一次滞后心跳花费 10 分钟**。

按「lag > 900 秒」规则，在 1026 条已闭环样本上：

- **标记滞后心跳 271 次**，其中 **83 次确认是误报**（精确率 30.6%）
- 漏报误报 29 次（占全部 112 次误报的 25.9%）

净节省时间 = 省下的误报排查 − 标记成本

```
83 × 75 − 271 × 10 = 6225 − 2710 = 3515 分钟 ≈ 58.6 小时
```

即：**在这批历史数据上，该规则可为值班团队净省约 58.6 小时的无效排查时间**，同时只多花 271 次 × 10 分钟的「标记确认」成本，且漏报的误报不到三成。

阈值扫描结果（展示净收益随阈值变化，证明 900s 是拐点）：

| 阈值 (lag >) | 标记数 | 其中误报 | 精确率 | 净省时间(分钟) |
|---|---|---|---|---|
| 300s | 698 | 103 | 14.8% | 745 |
| 600s | 439 | 94 | 21.4% | 2660 |
| **900s** | **271** | **83** | **30.6%** | **3515** |
| 1200s | 243 | 75 | 30.9% | 3195 |
| 1800s | 196 | 61 | 31.1% | 2615 |

阈值从 600s 升到 900s 时净收益持续上升，超过 900s 后因漏报增加、净收益回落，因此 900s 是兼顾「节省时间」与「漏报率」的最优点。

### 补充说明与局限

- 42 条未闭环样本（`is_valid` 为空）未纳入收益测算，但规则对它们同样可做预标记，作为「优先核实」提示。
- 华东节点误报率仅 5.4%（显著低于其他节点 10–15%），提示该节点心跳链路更健康，可做分节点的差异化阈值——这是后续可深化的方向，因时间限制未展开。
- 未使用任何自造数据；所有结论均基于发放的 `alarm_records.csv`。
